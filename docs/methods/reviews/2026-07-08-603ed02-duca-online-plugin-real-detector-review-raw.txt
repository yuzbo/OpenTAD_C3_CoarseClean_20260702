## A. Line-by-line code correctness review

### What is actually supported by the code

The commit really adds a `DucaOnlineFrameSelector` and wires it into `SingleStageDetector`: during train, the detector calls `frame_selector.forward_train(...)`, replaces `inputs`, `masks`, `metas`, `gt_segments`, and `gt_labels`, then forwards the selected tensors through backbone/projection/neck/head; during test it similarly calls `frame_selector.forward_test(...)` before the detector stack. This is a real integration path, not just a standalone ledger script. ([GitHub][1])

The selector also really performs hard temporal gathering: it obtains `grid.selected_positions`, creates `slot_mask = positions >= 0`, gathers `inputs` at those positions, applies gathered ST weights, and returns `selected_masks = slot_mask`. So the detector path can consume selected observations rather than dense observations. ([GitHub][2])

However, almost every paper-level claim beyond “a smoke plugin exists” is still blocked.

## P0-2 — Training-time GT coordinate contract is wrong or at least unproven: sparse selected-axis inputs are passed to the detector while GT segments are returned unchanged

**Files / functions**

* `opentad/models/selectors/duca_online_frame_selector.py`

  * `forward_train`
* `opentad/models/detectors/single_stage.py`

  * `forward_train`
* `opentad/models/duca/acquisition.py`

  * `SparseTemporalGrid`, `TrueTimeMap` helpers

**Evidence**

`DucaOnlineFrameSelector.forward_train` returns `gt_segments` and `gt_labels` unchanged after selecting inputs. ([GitHub][2])

`SingleStageDetector.forward_train` then forwards the selected `inputs`/`masks` and those returned `gt_segments`/`gt_labels` into the RPN head. ([GitHub][1])

The selector metadata includes selected-to-original and original-to-selected maps, but the selector does not actually remap GT segments before returning them. ([GitHub][2])

The true-time remap utilities support selected-axis ↔ true-time segment remapping, but this is used in post-processing for predictions, not shown as applied to training GT before the head’s assignment/regression loss. ([GitHub][6])

**Why this is wrong / risky**

Most TAD heads assign GT to temporal points/proposals in the detector’s input temporal axis. If the detector sees a sequence of length `K=384` but GT segments remain in dense-time coordinates `0..767`, then point assignment, center sampling, regression targets, and range constraints are inconsistent. This is exactly the type of geometry bug that destroys high-IoU mAP while smoke tests still pass.

**Failure caused**

Real training can silently learn wrong localization, especially at mAP@0.6/0.7. You can get a nonzero loss and nonzero gradients while optimizing a geometrically invalid task.

**Affected claims**

* mAP validity: **P0 blocker**
* high-IoU TAD validity: **P0 blocker**
* online-plugin validity: **P0 blocker for real detector**
* detector-loss-aware acquisition: **P0 blocker**

**Exact fix**

Pick one coordinate contract and enforce it end-to-end.

The safer final route is:

1. The sparse detector head operates in **true original-time units**, not selected-rank units.
2. Each selected observation carries `true_time`, `left_gap`, `right_gap`, local support interval, and valid mask.
3. Point generation / assignment / regression targets use true-time coordinates.
4. Predictions are decoded directly in true-time.
5. GT stays original-time, but the head is made irregular-grid-aware.

The minimal interim route is:

1. Before detector training, remap GT true-time segments into selected-axis coordinates with `TrueTimeMap.true_to_selected`.
2. Train the existing head in selected-axis coordinates.
3. Remap predictions back to true-time before evaluation.
4. Store both original GT and remapped GT in `metas` for audit.
5. Add tests that compare dense uniform remap against identity behavior.

Do not keep `remap_gt_to_selected_axis=True` as a config flag unless it actually remaps GT.

## P0-3 — Prediction remap is insufficient for high-IoU sparse TAD

**Files / functions**

* `opentad/models/detectors/single_stage.py`

  * `_remap_selector_segments_for_post_processing`
* `opentad/models/utils/true_time.py`

  * `selected_to_true`, `true_to_selected`, `remap_segments`
* `opentad/models/dense_heads/duca_online_precheck_head.py`

  * `forward_test`

**Evidence**

The detector post-processing remaps selected-axis proposal segments back to true-time using metadata. ([GitHub][1])

The remapping utility performs piecewise linear interpolation between selected positions. ([GitHub][6])

The precheck head emits dummy selected-axis unit proposals, not real boundary predictions. ([GitHub][4])

**Why this is wrong / risky**

A selected-rank segment `[i, j]` is not a real temporal interval unless the head understands the actual gaps between selected observations. Interpolation is acceptable as a temporary bridge, but it does not solve high-IoU localization. If selected observations skip across an action boundary, no linear remap can recover the missing boundary.

**Failure caused**

The model may appear to support “original-time decode,” but high-IoU mAP can be invalid or systematically capped by sparse holes. This is especially dangerous because mAP@0.3/0.4 may look acceptable while mAP@0.7 collapses.

**Affected claims**

* high-IoU localization: **blocked**
* original-time selected decode: **partial**
* selected-axis remap validity: **partial**
* ActionFormer compatibility: **unsupported**

**Exact fix**

Implement an irregular temporal grid head:

* Point generator emits points at selected true-time positions, not dense selected ranks.
* Each point has support interval `[mid(prev, cur), mid(cur, next)]`.
* Regression predicts true-time left/right offsets.
* Loss and IoU are computed in original-time / seconds.
* Post-processing no longer needs rank-to-time interpolation except for visualization.

For AdaTAD, add a sparse grid adapter that injects selected true-time positions and local density into the detection head. For ActionFormer, modify the point generator and regression target builder.

## P0-4 — “Original-time positions” currently mean dense feature-grid indices, not raw-frame time; the raw-frame / pre-backbone claim is not yet valid

**Files / functions**

* `opentad/models/selectors/duca_online_frame_selector.py`

  * `__init__`, `_write_metas`
* `opentad/models/duca/acquisition.py`

  * `budgeted_center_radius_decode`

**Evidence**

The selector enforces `selected_positions_unit == "original_time_index"` and writes selected positions into metadata. ([GitHub][2])

But the decoder requires `dense_positions` to be a contiguous arange of original-time indices. This is an index contract over the current input temporal grid, not necessarily raw video frame indices or seconds. ([GitHub][7])

The config uses `dense_window_size=768`, `window_size=384`, and the detector inputs are temporal observations in the OpenTAD/AdaTAD feature-grid sense. ([GitHub][8])

**Why this is wrong / risky**

The paper motivation says “pre-backbone sparse temporal acquisition,” but this commit operates on whatever tensor arrives as `inputs`. In OpenTAD/AdaTAD, that is often already a feature/snippet grid, not raw video frames before the expensive backbone. Calling those positions “original time” can be acceptable only if the paper defines original dense-time as the detector’s dense temporal observation grid. It is not evidence of raw-frame compute reduction.

**Failure caused**

Efficiency claims become invalid: the expensive backbone may already have been run before selection. A reviewer will attack this immediately.

**Affected claims**

* pre-backbone sparse temporal observation selection: **partially supported only for feature-grid selection**
* compute efficiency: **unsupported**
* raw-frame acquisition: **unsupported**

**Exact fix**

Introduce an explicit coordinate object:

```text
raw_frame_index
video_time_sec
snippet_index
adatad_feature_index
selected_axis_index
```

Every config must declare the acquisition point:

* raw frames before VideoMAE / SlowFast;
* snippet features before AdaTAD head;
* feature tokens after backbone.

Budget must be reported in the correct unit. If selection is after feature extraction, do not claim backbone FLOPs savings.

## P0-5 — Detector-loss-aware gradient is not meaningful enough yet

**Files / functions**

* `opentad/models/selectors/duca_online_frame_selector.py`

  * `_forward_select`
* `opentad/models/duca/acquisition.py`

  * `forward_acquire`, `duca_losses`

**Evidence**

The selector gathers hard-selected inputs, then multiplies them by gathered `selected_mask_st`. ([GitHub][2])

The acquisition code builds `selection_st = hard_union + soft_coverage - soft_coverage.detach()`. This is a straight-through mask over dense positions, then it is gathered only at already selected positions. ([GitHub][7])

**Why this is wrong / risky**

This proves a gradient path exists, but not that detector loss can teach the selector to choose better alternative positions. Because the forward gather indices are hard and non-differentiable, detector loss gradients mostly affect soft coverage values at already selected positions. They do not naturally give credit to unselected alternatives unless the soft relaxation is designed to do so.

**Failure caused**

The selector may not become detector-loss-aware in the scientific sense. It can collapse to actionness top-k, uniform-with-repair, or radius-fill heuristics while passing gradient smoke tests.

**Affected claims**

* detector-loss-aware acquisition: **unsupported beyond graph connectivity**
* final method novelty: **blocked**
* hard-forward ST fine-tuning: **incomplete**

**Exact fix**

Add a real differentiable budgeted selection estimator:

* Gumbel-TopK / perturb-and-MAP TopK;
* NeuralSort / SoftSort relaxation;
* Sinkhorn top-K assignment;
* REINFORCE with detector-loss reward and variance baseline;
* or a two-stream hard-forward / soft-backward estimator where the soft path computes a weighted feature mixture over all candidate positions, not only gathered selected slots.

Then add tests that show changing detector loss changes unselected-position logits, not merely selected-slot amplitudes.

## B. Zero-shot actionness review

### What is good

The zero-shot evaluator makes a serious attempt to separate score generation from evaluation labels. It defines forbidden leakage keys such as GT segments, labels, oracle fields, teacher fields, prediction caches, and raw predictions, and recursively rejects them. ([GitHub][9])

For built-in motion / feature-energy scoring, labels are used only after scoring to compute metrics. The output rows include `gt_action` for evaluation, while source provenance says scoring does not read GT or teacher. ([GitHub][9])

AUROC, AUPRC, Recall@K, and Precision@K are computed from rows with `gt_action` labels and `p_action` scores. The AUROC implementation handles ties by pairwise ranking, and AUPRC is threshold-free over sorted predictions. ([GitHub][9])

The selection evaluator also marks oracle baselines as diagnostic-only and records whether a baseline uses GT for selection. ([GitHub][10])

### What is not sufficient

**Zero-shot actionness is not yet evidence that frozen/no-target-label actionness can replace a THUMOS-trained coarse classifier.** At this commit, the implemented sources are motion/feature-energy/manual/precomputed/mock scaffolds. Real X-CLIP, ActionCLIP, SlowFast, and VideoMAE sources are reserved names that intentionally fail unless local scores are provided. ([GitHub][9])

Manual/precomputed provenance is not strict enough. `thumos_trained=None` is allowed, so an unknown source can be reported without proving it is no-THUMOS. For a paper, unknown provenance must be a hard fail. ([GitHub][9])

The metrics are actionness metrics, not detection metrics. AUROC/AUPRC/Recall@K can show coarse temporal correlation with action interior, but they do not prove boundary coverage, high-IoU localization, or detector mAP improvement.

Selection evaluation is better because it includes geometry metrics such as boundary recall, short-action recall, holes, redundancy, and uniform similarity. But those still remain diagnostic until connected to real detector mAP. ([GitHub][10])

### Required fixes before making a zero-shot claim

For every zero-shot source, require:

```text
source_family
checkpoint_name
checkpoint_hash
training_dataset
target_dataset_labels_used=false
target_dataset_videos_used=false/true with explanation
calibration_split
score_generation_code_hash
per-video inference cost
per-video feature cost
```

Then report separate tables:

1. actionness quality: AUROC/AUPRC/Recall@K;
2. selection geometry: boundary support, short-action recall, holes, uniform similarity;
3. detector outcome: mAP@0.5/0.6/0.7 and average mAP;
4. cost: zero-shot model cost plus detector cost.

Do not claim “zero-shot replaces THUMOS coarse classifier” until real frozen X-CLIP / ActionCLIP / SlowFast / VideoMAE sources beat or match p_action top-K under the same budget and cost accounting.

## D. More intelligent final selection designs

The current center/radius/actionness-source plugin is still too heuristic. A final paper method should be less like “top-k with repairs” and more like “detector-loss-aware sparse temporal grid learning.”

## Recommended method 1 — DUCA-STG: detector-loss-aware sparse temporal grid with hard-forward / soft-backward TopK

### Model definition

For each dense temporal observation `x_t`, compute:

```text
h_t = temporal_encoder(x_t, motion_t, zero_shot_actionness_t, position_t)
logit_t = acquisition_score_head(h_t)
radius_t = learned_radius_head(h_t) in [0, 16]
boundary_t = boundary_uncertainty_head(h_t)
utility_t = detector_responsibility_head(h_t)
```

The selector samples or ranks a strict set:

```text
S = TopK(logit_t + utility_t + boundary_t, K <= 384)
```

Then it expands only through a budgeted sparse-grid allocator:

```text
selected = budgeted_union(centers=S, radius=radius_t, hard_cap=384)
```

### Strict budget

Budget is enforced inside the allocator, not config-only:

```text
len(selected) <= 384 always
budget violation = hard error
```

### Train forward

* Forward path uses hard selected observations only.
* Detector consumes `gather(x, selected)`.
* Backward path uses differentiable TopK relaxation:

  * Gumbel-TopK,
  * perturb-and-MAP,
  * SoftSort/NeuralSort,
  * or sparsemax/entmax budget relaxation.
* Detector loss backpropagates through the relaxation.

### Test forward

* No teacher.
* No GT.
* No caches.
* Deterministic hard TopK / budgeted allocator.
* Sorted original-time positions.

### Loss

```text
L = L_detector
  + λ_budget * max(0, K - 384)
  + λ_entropy * collapse_regularizer
  + λ_hole * action-local hole penalty from no-leak proxy
  + λ_radius * radius sparsity
```

Detector feedback comes from real AdaTAD/ActionFormer classification/regression/IoU losses.

### Leakage avoidance

Teacher utility, if used, is train-only and stored under audited provenance. Inference rejects teacher/cache/oracle payloads.

### Code modules to change

* `opentad/models/selectors/duca_online_frame_selector.py`
* `opentad/models/duca/acquisition.py`
* real AdaTAD sparse head / adapter
* ActionFormer point generator / target assigner
* no-leak provenance validator

## Recommended method 2 — DUCA-Responsibility: learn acquisition from detector responsibility, not actionness

### Model definition

Use a dense teacher detector only during training to compute a temporal responsibility signal:

```text
R_t = gradient/proposal responsibility of dense detector loss with respect to temporal observation t
```

The selector learns:

```text
q_t = selector(x_t, motion_t, frozen_actionness_t)
q_t ≈ R_t
```

Then final fine-tuning uses real sparse detector loss.

### Why this is better

It avoids the “actionness interior over-selection” failure. The selector learns which observations affect detection and localization, not merely which frames look like actions.

### Strict budget

Hard TopK or dynamic-K capped at 384.

### Train/test

* Train stage 1: dense teacher generates responsibility targets on train split.
* Train stage 2: hard-forward sparse detector fine-tuning.
* Test: selector only; no teacher.

### Leakage control

Teacher can be used to train the selector, but not at inference. Teacher targets must be generated only on training videos and logged as train-only distillation artifacts.

### Code changes

* add dense teacher responsibility extraction;
* add selector responsibility loss;
* add audit artifact proving no teacher payload in test;
* add ablation: with/without teacher warm-up.

## Recommended method 3 — Irregular-time ActionFormer-compatible sparse grid

### Model definition

Do not pretend selected positions are uniformly spaced. Each selected point `s_i` carries:

```text
true_time_i
left_support_i = true_time_i - midpoint(prev, current)
right_support_i = midpoint(current, next) - true_time_i
local_density_i
gap_left_i
gap_right_i
```

The head predicts:

```text
class_i
left_offset_i in true-time units
right_offset_i in true-time units
```

### Strict budget

The point set is the selected set, capped at 384.

### Train/test

* Train assignment uses true-time GT.
* Test decode outputs true-time intervals directly.
* No selected-rank remap needed except visualization.

### Detector feedback

Real ActionFormer classification/regression losses backpropagate to selector through ST selection.

### Leakage avoidance

No GT used in selection. GT only used by detector loss.

### Code changes

* `PointGenerator` replacement;
* ActionFormer head target builder;
* sparse NMS coordinate audit;
* selected-time metadata schema.

## Recommended method 4 — Dynamic-K DUCA with matched-average budget reporting

### Model definition

Selector predicts an acquire/skip probability and stop probability:

```text
a_t ~ Bernoulli(p_t)
K = sum_t a_t
```

Training uses a Lagrangian:

```text
L = L_detector + λ * max(0, E[K] - K_target) + μ * budget_violation
```

### Strict budget

At inference:

```text
K <= 384 by hard cap
```

Dynamic-K must be compared against fixed-K methods with the same average selected count.

### Why it is publishable

Dynamic acquisition is a stronger claim than fixed 384. But reviewers will only accept it if matched-average fixed-K baselines are present.
