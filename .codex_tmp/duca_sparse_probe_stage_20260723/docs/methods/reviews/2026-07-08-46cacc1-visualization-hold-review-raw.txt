## 1. 当前 metrics 是否足以解释 PAction fixed384 强于 GAS-VT fixed384？

**不够，只能构成强相关诊断，不足以构成决定性解释。**

你现在的锚点已经很有用：

| method                   | Avg mAP | both endpoint coverage @ r16 | boundary recall @ r1 | p95 unselected hole |
| ------------------------ | ------: | ---------------------------: | -------------------: | ------------------: |
| GAS-VT fixed384          |   44.90 |                      0.17164 |              0.22794 |               92.54 |
| PAction learned fixed384 |   59.10 |                      0.26471 |              0.42148 |                2.18 |
| lattice move50           | pending |                      0.26520 |              0.42895 |                2.00 |
| lattice move75           | pending |                      0.26520 |              0.42727 |                2.00 |

这组数字非常清楚地说明：GAS-VT 的失败和“大洞 + 边界覆盖不足”高度一致；PAction learned fixed384 的提升和“边界 recall 更高 + p95 hole 大幅缩小”高度一致。但它还没有证明：

1. 是 **hole** 导致检测失败，还是 hole 只是另一个 selector 崩坏症状；
2. 是 **endpoint coverage** 驱动高 IoU 定位，还是 action interior / score calibration / postprocess 差异驱动；
3. lattice move50/move75 的 geometry 接近 PAction，但 detector mAP pending，因此当前还不能证明 geometry 指标足以预测 mAP；
4. 没有 per-instance matched accounting：某个动作实例如果 endpoint miss / large hole，是否真的更容易成为 FN 或低 tIoU TP；
5. 没有 counterfactual repair：只修补 GAS-VT 的 hole 或 endpoint 后，mAP 是否回升。

决定性诊断应是：

**matched instance-level causal accounting**：对每个 GT action instance 记录 selector 几何、detector 最佳 proposal tIoU、TP/FN 状态、start/end error，然后画出 “coverage geometry → proposal quality → mAP@high IoU” 的链条。

## 2. 当前 geometry metrics 是否合适？还缺什么？

`p95_unselected_hole`、`both endpoint coverage`、`boundary recall @ r1/r16`、region share 是正确方向，但还不够 paper-level。

### 应保留的指标

`p95_unselected_hole` 很关键，因为 TAD detector 的 temporal regression 需要局部连续证据。GAS-VT 的 p95 hole 为 92.54，而 PAction/lattice 约 2，这个差异巨大，应该作为 paper-facing 主指标之一。

`both endpoint coverage` 比单边 boundary recall 更接近高 IoU 定位目标。只覆盖 start 或 end 不够，mAP@0.6/0.7 需要两端同时对齐。

`boundary recall @ r1/r16` 应保留，但必须解释 r 的单位：是 768 AdaTAD grid index，还是原视频帧/秒。当前 paper story 若声称 pre-backbone，单位必须严谨。

`region share` 可以作为辅助，但不应放主图。它容易变成“动作覆盖”而不是“边界定位”证据。

### 必须新增的指标

**A. Endpoint nearest distance**

对每个 GT action 的 start/end，记录到最近 selected position 的距离：

```text
start_nearest_dist_grid
end_nearest_dist_grid
start_nearest_dist_norm = dist / action_length_grid
end_nearest_dist_norm = dist / action_length_grid
max_endpoint_dist_norm = max(start_norm, end_norm)
```

比 recall@r 更连续、更可解释。

**B. Bracketed endpoint coverage**

仅“附近有点”还不够，边界最好被前后两侧观测 bracket：

```text
start_bracketed_r = exists selected in [s-r, s] and exists selected in [s, s+r]
end_bracketed_r   = exists selected in [e-r, e] and exists selected in [e, e+r]
both_bracketed_r  = start_bracketed_r and end_bracketed_r
```

这比 endpoint recall 更贴近 boundary regression。

**C. Action-interior max hole**

全视频 p95 hole 会被背景长段主导。应导出：

```text
max_unselected_hole_inside_action
p95_unselected_hole_inside_action
max_unselected_hole_near_boundary_band
```

否则短动作和长背景视频会混淆。

**D. Length-stratified geometry**

必须按 action duration 分桶：

```text
short / medium / long
或者 duration quantile: Q1/Q2/Q3/Q4
```

高 IoU 下降通常先发生在短动作上。只给全局平均会掩盖最关键失败。

**E. Per-class geometry**

THUMOS14 类别差异明显。必须导出 per-class endpoint coverage、hole、mAP@0.7，否则不能证明不是某几个类别偶然驱动。

**F. Detector-coupled proposal quality**

这是当前最缺的 decisive diagnostic：

```text
best_proposal_tIoU_per_gt
best_proposal_score_per_gt
matched_tp_at_0.5 / 0.6 / 0.7
start_error_sec
end_error_sec
center_error_sec
duration_error_ratio
```

几何指标必须和 detector output 接起来，否则仍是 selector-side proxy。

**G. Compute/latency contract**

如果论文 claim 是 acquisition，需要导出：

```text
selected_count
effective_budget
backbone_positions_processed
selector_cost
detector_cost
total_latency_proxy
FLOPs_proxy
memory_proxy
```

否则“384 observations”只是 budget story，不是 deployable story。

## 4. 当前 plots 的主要误导风险

即使你本地已经有这些脚本，paper-facing plots 必须防止以下问题。

### P0 风险：missing mAP 被画成 0 或参与 heatmap normalization

lattice move50/move75 目前 detector mAP pending。主图中可以显示 geometry，但不能把 missing mAP 当作 0，也不能在 heatmap 里用 0 参与 min-max normalization。正确做法：

```text
mAP = NA
plot marker = hollow / gray outline
legend = geometry-only diagnostic, detector mAP pending
```

### P0 风险：diagnostic methods 与 paper-main methods 混在同一 ranking

lattice move50/move75 是 diagnostic route，不是 final method。Stage2/Stage3 也还不是 completed mAP evidence。主表应该分区：

```text
Completed detector mAP:
- dense AdaTAD
- uniform_384
- random_384
- GAS-VT fixed384
- PAction learned fixed384
- p_action top-k fixed384, if run

Geometry-only diagnostic:
- lattice move50
- lattice move75

In-progress:
- Stage2 detector-aware
- Stage3 joint
```

### P0 风险：768-grid selection 被写成 raw-frame pre-backbone

当前 README 本身说 C3 阶段是在 384/768 selection ledger 上接 OpenTAD/AdaTAD，且该阶段是 fixed-budget control anchor，不是最终论文贡献全部形态。([GitHub][5]) 如果论文说“pre-backbone raw-frame acquisition”，当前证据不足；更准确的表述应是：

> pre-detector / pre-AdaTAD temporal-grid acquisition on the 768 AdaTAD temporal grid.

要把它升级成真正 pre-backbone paper claim，需要 raw-frame 或 pre-feature evidence，见最后一节。

### P1 风险：全视频 p95 hole 混淆背景长段和 action-local holes

TAD localization 应关心 action boundary 附近和 action interior。如果 p95 hole 是全视频 unselected runs，长背景会支配指标。必须同时导出 action-local hole。

### P1 风险：短视频 / 短 window 权重过高

如果按 window row 平均，而不是按 GT instance 或 video 加权，短视频、多 window 视频、无动作背景窗口都会改变统计。应明确：

```text
aggregation_level = action_instance / video / window / row
```

主论文建议以 action instance 为主，video-level bootstrap CI 为可信区间。

### P1 风险：heatmap normalization 隐藏绝对量级

`p95 hole: 92.54 vs 2.18` 是绝对差异，不能只用 min-max heatmap。scorecard heatmap 必须同时写 raw value，最好按“higher better / lower better”分区，而不是全部归一化到一个颜色方向。

## 6. Per-video selection behavior：如何避免 anecdotal？

不要只放 3 个“好看”的 timeline。应该做三层：

### 第一层：dataset-level density map

把每个 GT action 归一化到 `[0,1]`，并扩展上下文到 `[-0.25,1.25]`。统计 selected positions 的密度：

```text
x = (selected_grid_pos - gt_start) / (gt_end - gt_start)
```

按 method、action length bin、class 聚合。这个图能直接显示 selector 是否围绕 start/end 聚集，是否在 action interior 留洞。

### 第二层：objective representative timelines

timeline gallery 的样本选择必须可复现：

```text
best_case: PAction TP@0.7 and GAS-VT FN, largest endpoint coverage gap
failure_case: PAction FN@0.7 despite good geometry
hole_case: GAS-VT p95 action-local hole top-k
short_action_case: duration in bottom quartile
```

每张 timeline 标出：

```text
GT action segments
selected positions
unselected holes
nearest selected to start/end
detector proposals
emission/mAP status if online is later claimed
```

### 第三层：failure gallery as audit, not proof

Failure gallery 放 appendix。主论文只用一张 representative timeline 作为可读性辅助；真正证据来自 density map 和 matched failure accounting。

## 7. 高 IoU localization preservation 必须怎么画？

主论文必须有以下三类 evidence。

### A. mAP@tIoU decomposition

不能只报 Avg-mAP。至少画：

```text
mAP@0.3, 0.4, 0.5, 0.6, 0.7
```

重点标出：

```text
PAction - GAS-VT at 0.6/0.7
PAction - uniform_384 at 0.6/0.7
PAction - dense AdaTAD at 0.6/0.7
```

### B. Boundary error distribution

对 matched TP 或 best proposal per GT 导出：

```text
abs_start_error_sec
abs_end_error_sec
normalized_start_error = abs_start_error / action_duration
normalized_end_error = abs_end_error / action_duration
```

画 CDF 或 violin。高 IoU claim 需要证明 start/end error 不是只在低阈值改善。

### C. Proposal-quality curve

对每个 GT 找 best proposal tIoU，画 CDF：

```text
P(best_tIoU >= threshold)
```

这个图比 mAP 更能解释 detector-side localization upper bound。若 PAction 的 best-proposal tIoU CDF 明显右移，而 GAS-VT 左移，就能支撑“selection geometry affects localization quality”。

## 10. Pseudocode for missing analyses

### A. Per-instance geometry exporter

```python
def nearest_distance(selected: np.ndarray, x: int) -> tuple[int | None, float]:
    if selected.size == 0:
        return None, float("inf")
    idx = int(np.argmin(np.abs(selected - x)))
    return int(selected[idx]), float(abs(selected[idx] - x))

def is_bracketed(selected: np.ndarray, x: int, r: int) -> bool:
    left = np.any((selected >= x - r) & (selected <= x))
    right = np.any((selected >= x) & (selected <= x + r))
    return bool(left and right)

def max_hole_in_interval(selected: np.ndarray, lo: int, hi: int) -> int:
    lo, hi = int(lo), int(hi)
    if hi < lo:
        return 0
    mask = selected[(selected >= lo) & (selected <= hi)]
    observed = np.concatenate([[lo - 1], np.sort(mask), [hi + 1]])
    gaps = observed[1:] - observed[:-1] - 1
    return int(np.max(gaps)) if gaps.size else 0

def export_geometry_per_instance(method_rows, gt_instances, out_csv):
    rows = []
    for method_id, video_id, selected in method_rows:
        selected = np.asarray(sorted(set(map(int, selected))), dtype=np.int64)
        for gt in gt_instances[video_id]:
            s, e = int(round(gt.start_grid)), int(round(gt.end_grid))
            dur = max(1, e - s + 1)

            s_near, s_dist = nearest_distance(selected, s)
            e_near, e_dist = nearest_distance(selected, e)

            row = {
                "method_id": method_id,
                "video_id": video_id,
                "class_id": gt.class_id,
                "gt_start_grid": s,
                "gt_end_grid": e,
                "gt_duration_grid": dur,
                "start_nearest_selected_grid": s_near,
                "end_nearest_selected_grid": e_near,
                "start_nearest_dist_grid": s_dist,
                "end_nearest_dist_grid": e_dist,
                "start_nearest_dist_norm": s_dist / dur,
                "end_nearest_dist_norm": e_dist / dur,
                "max_endpoint_dist_norm": max(s_dist, e_dist) / dur,
                "max_hole_inside_action": max_hole_in_interval(selected, s, e),
            }

            for r in (1, 4, 8, 16):
                row[f"start_covered_r{r}"] = s_dist <= r
                row[f"end_covered_r{r}"] = e_dist <= r
                row[f"both_covered_r{r}"] = row[f"start_covered_r{r}"] and row[f"end_covered_r{r}"]
                row[f"start_bracketed_r{r}"] = is_bracketed(selected, s, r)
                row[f"end_bracketed_r{r}"] = is_bracketed(selected, e, r)
                row[f"both_bracketed_r{r}"] = row[f"start_bracketed_r{r}"] and row[f"end_bracketed_r{r}"]

            rows.append(row)

    pd.DataFrame(rows).to_csv(out_csv, index=False)
```

```python
def tiou(a_start, a_end, b_start, b_end):
    inter = max(0.0, min(a_end, b_end) - max(a_start, b_start))
    union = max(a_end, b_end) - min(a_start, b_start)
    return 0.0 if union <= 0 else inter / union

def export_detector_matches(gt_by_video, pred_by_video, out_csv):
    rows = []
    for video_id, gt_list in gt_by_video.items():
        preds = pred_by_video.get(video_id, [])
        for gt in gt_list:
            same_cls = [p for p in preds if p.label == gt.label]
            best = None
            best_iou = -1.0
            for p in same_cls:
                val = tiou(gt.start, gt.end, p.start, p.end)
                if val > best_iou:
                    best_iou = val
                    best = p

            dur = max(1e-6, gt.end - gt.start)
            rows.append({
                "video_id": video_id,
                "class_id": gt.label,
                "gt_start_sec": gt.start,
                "gt_end_sec": gt.end,
                "gt_duration_sec": dur,
                "best_tiou": best_iou,
                "best_proposal_score": None if best is None else best.score,
                "start_error_sec": None if best is None else abs(best.start - gt.start),
                "end_error_sec": None if best is None else abs(best.end - gt.end),
                "start_error_norm": None if best is None else abs(best.start - gt.start) / dur,
                "end_error_norm": None if best is None else abs(best.end - gt.end) / dur,
                "tp_at_05": best_iou >= 0.5,
                "tp_at_06": best_iou >= 0.6,
                "tp_at_07": best_iou >= 0.7,
                "fn_at_07": best_iou < 0.7,
            })
    pd.DataFrame(rows).to_csv(out_csv, index=False)
```

## 12. Is 768-grid selection enough for a pre-backbone paper claim?

**Frank assessment: not enough for a strong “pre-backbone raw-frame acquisition” claim.**

It is acceptable for a paper if you frame it precisely as:

> sparse temporal acquisition on the AdaTAD/OpenTAD temporal grid before the expensive detector head / temporal detector processing.

It is weaker, and reviewers may call it secondary processing, if the video has already gone through the same feature/snippet extraction pipeline as dense AdaTAD. The project README itself frames the current C3 stage as fixed-budget control using `p_action` converted to a 384/768 ledger and then fed to AdaTAD/OpenTAD, while also saying this stage is not the whole final contribution.([GitHub][5])

To claim **pre-backbone** convincingly, you need at least one of these:

1. **Raw-frame route evidence**: selector runs before expensive frame/video encoder; selected raw frames/snippets are the only ones encoded.
2. **Feature-computation accounting**: show dense AdaTAD encodes 768 units, while your method encodes ≤384 units, with FLOPs/latency reduction measured or credibly proxied.
3. **No dense feature dependency at test time**: selector cannot use features that require the expensive backbone over all 768 positions.
4. **Matched raw/pre-feature baseline**: uniform_384, random_384, PAction_384, GAS-VT_384 all operate before feature extraction, not after dense feature generation.
5. **End-to-end deployment diagram**: raw video → low-cost selector → expensive backbone on selected units only → detector.

Without that, the safest title/claim is not “pre-backbone sparse frame acquisition,” but:

> task-aware sparse temporal-grid acquisition for AdaTAD/OpenTAD.

That can still be publishable if the detector mAP story is strong, especially if you prove high-IoU preservation and show the selector is low-cost and deployable. But for a top-tier “pre-backbone computation reduction” claim, raw-frame or pre-feature evidence is required.
